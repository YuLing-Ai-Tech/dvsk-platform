# DVSK v0.1 — 动态视觉语义知识库（B 阶段）

**状态：产品与数据设计草案；非已部署系统。**

## 1. 产品目标

让用户用自然语言、参考图片或网页链接表达审美意图，系统负责专业语义猜测、可视化样例对照、确认并生成可执行视觉规约。词典可从经许可的网络来源和用户授权的图片中持续补充，但正式知识必须经过验证与版本化。

## 2. 设计原则

- 以结果为先：先给候选和样例，最少追问。
- 术语不是唯一真相：区分业内通用名称、描述性标签和 AI 临时命名。
- 图像不能自动等于设计意图：观察事实与推断意图必须分开。
- 网络搜索只添加候选，不能未经审查覆盖现有知识。
- 用户图像默认为私有，不跨客户复用。
- 源作品保留链接、许可证、授权范围；不能默认复制外部截图用于商业训练或模板。
- PPT 的布局语义与网页 UI 灵感相互借鉴，但不能不加转换地直接用于演示文稿。

## 5. 在线发现流水线

触发条件：用户主动点击找灵感、现有词典匹配较差、或用户授权的定期发现任务。

1. 在指定来源中检索关键词、相似视觉特征、布局类别。
2. 遵守站点访问权限、服务条款、robots 要求；优先使用官方检索/API、可引用链接或允许分析的资料。
3. 提取页面的布局、视觉层次、色彩、排版和动态线索，记录截图条件（视口、时间、页面状态）。
4. 和现有术语做文本+图像相似检索，区分“新样例”“现有术语的别名”“可能的新模式”。
5. 生成候选知识：定义、典型表达、参数、适用边界、来源和置信依据。
6. 去重、质量校验、版权许可检查；低风险样例关联可以自动提交待审，新增术语必须经过确认才进入正式库。
7. 版本发布，可追溯、回滚，不静默覆盖旧定义。

建议参考来源：Mobbin（真实 UI 设计模式），Awwwards（网站美学灵感），Behance/Dribbble（设计作品），Material Design（设计规范）。不同来源的授权与访问方式分别评估。

## 6. 用户图片解构流水线

输入：PPT 页截图、网页截图、示例图片，后续支持多页 PDF/PPT。

1. 区域分割：文本、图片、卡片、图表、形状、背景、装饰。
2. 几何分析：包围框、对齐、栅格、间距、大小比例、层叠关系。
3. 视觉分析：颜色、字体特征（不臆断精确字体）、对比度、层级、动线。
4. 术语检索：返回前 3–5 个可能的布局/风格概念及对应证据区域。
5. 用户确认：哪个更像、哪里不对、是否继续找相似样例。
6. 语义对齐：映射到已有术语、存储别名或建立待审新概念。
7. 规约导出：布局结构、参数、内容区域、视觉禁忌、来源和不确定项。

注意：截图无法可靠还原动画、交互、精确字体或设计者意图；需标记 unknown 并请求补充视频/源文件。

## 7. 语义匹配与增补策略

- 精确匹配：既有概念、视觉特征与用途一致 → 关联样例。
- 同义匹配：名字不同但核心约束相同 → 新增别名。
- 组合匹配：流式布局 + 浮层卡片 → 组合已有术语，不必创造新词。
- 真正新颖：已有术语无法表达且经多案例验证 → 待审新概念。
- 无法确认：保留描述性标签与不确定性，不冒称行业标准。

## 8. 最小 API 约定（建议）

- `POST /visual-semantic/interpret`：模糊语言 → 语义候选及解释。
- `POST /visual-semantic/analyze-image`：图片 → 区域、特征与术语候选。
- `POST /visual-semantic/discover`：按需网络发现任务 → 有来源的候选记录。
- `GET /visual-semantic/terms`：术语搜索与筛选。
- `POST /visual-semantic/confirm`：用户确认或纠正匹配。
- `POST /visual-semantic/spec`：输出结构化视觉规约。
- `POST /visual-semantic/candidates/{id}/review`：知识发布审核。

## 9. 交付分期

**B0（可用）**：初始词典、同义词、手工创建样例、文本匹配、术语建议、规约输出。

**B1（可学习）**：图片上传解构、相似检索、用户确认、私有候选知识、去重审核。

**B2（可发现）**：授权网络来源的按需搜索、设计参考索引、来源/许可审查、新模式候选。

**B3（可持续）**：周期性检索、回归测试、知识版本、质量监控、多领域扩展。

## 10. 验收指标

- Top-3 术语命中率：对人工标注数据衡量。
- 样例选择成功率与首次结果接受率。
- 用户平均澄清时间与最终修订轮次。
- 视觉规约与真实生成的一致性（独立人工评审）。
- 错误增补率、重复概念率、来源可追溯率、版权合规率。

## 11. 与 A 的关系

A（完整需求分析架构）必须调用 B，但 B 自身保持独立；A 管目标/内容/约束/确认，B 管视觉术语/图片解构/案例发现/视觉规约，两者通过结构化 Contract 接口衔接。完整 A 文档在 B 方向确认后编写。
